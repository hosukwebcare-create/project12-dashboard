# 배포·실사용 체크리스트

개발 DB에서 검증이 끝난 상태에서 실제 지점이 쓰기까지의 순서입니다. 세 가지 호스팅 중 하나를 고르고, 나머지 단계는 공통입니다. 예상 소요는 호스팅 세팅 반나절, 데이터 적재와 계정 준비 반나절, 병행 운영 1주입니다.

## 0. 호스팅 고르기

| 방식 | 맞는 경우 | 비용 감 | 준비물 |
|---|---|---|---|
| **Railway** (권장, 가장 빠름) | 지점 수 십 개 이하, 운영 인력 없음 | 월 2~4만 원 (Hobby/Pro + Postgres) | Railway 계정, GitHub 저장소, 카드 |
| **GCP Cloud Run + Cloud SQL** | 본사가 GCP를 이미 쓰거나 PITR·감사 요건이 있을 때 | 월 5~10만 원 | GCP 프로젝트, 결제 계정 |
| **사내 서버 docker compose** | 폐쇄망 또는 자체 서버 보유 | 서버 유지비 | 도커가 깔린 리눅스 서버, 고정 IP, 도메인 |

파일 저장소는 Railway·사내 서버는 볼륨(local 드라이버), GCP는 GCS(`STORAGE_DRIVER=gcs`)를 씁니다.

## 1. Railway 절차

1. Railway 새 프로젝트 → **Postgres** 추가. 기본 계정 `postgres`는 **superuser라서 RLS를 무시합니다.** 앱은 반드시 별도 계정으로 접속해야 합니다. 첫 배포와 마이그레이션이 끝난 뒤 아래를 한 번 실행하고, 서비스의 `DATABASE_URL`을 그 계정으로 바꿉니다.

   ```bash
   psql "$DATABASE_PUBLIC_URL" -v app_password=<긴 비밀번호> -f scripts/db-app-role-prod.sql
   ```

   그 뒤 서비스 변수: `DATABASE_URL=postgresql://byeolha_app:<비밀번호>@${{Postgres.RAILWAY_PRIVATE_DOMAIN}}:5432/${{Postgres.PGDATABASE}}`. 테이블 소유권도 이 계정으로 넘어가므로 이후 자동 마이그레이션도 이 계정으로 됩니다.
2. **New Service → GitHub Repo**로 이 저장소를 연결합니다. 루트의 `railway.toml`이 Dockerfile 빌드와 `/api/health` 상태 확인을 지정합니다.
3. 서비스 **Variables**에 아래를 넣습니다.

   | 변수 | 값 |
   |---|---|
   | `DATABASE_URL` | Postgres 서비스의 `${{Postgres.DATABASE_URL}}` 참조 |
   | `SESSION_SECRET` | 32자 이상 무작위 문자열 (`openssl rand -base64 48`) |
   | `JOB_SECRET` | 배치 호출용 무작위 문자열 |
   | `STORAGE_DRIVER` | `local` |
   | `STORAGE_DIR` | `/app/storage` |
   | `ALIMTALK_PROVIDER` | 알림톡 계약 전에는 `mock`, 계약 후 `nhn` 또는 `solapi`와 각 키 |
   | `RETENTION_DAYS` | `365` |
   | `WEBHOOK_ALLOW_PRIVATE` | `false` |

   `TZ=Asia/Seoul`은 운영 이미지(Dockerfile)에 박혀 있습니다. 다른 방식으로 배포한다면 반드시 지정하세요 — 서버가 UTC로 돌면 밤 9시부터 자정까지 화면의 '오늘'이 하루 전으로 나옵니다. `/api/health`의 `timeZone`·`localTime`으로 확인합니다.

4. 서비스 **Settings → Volumes**에서 `/app/storage`에 볼륨을 붙입니다(회원 파일 보관).
5. 마이그레이션은 서버가 켜질 때 자동으로 적용됩니다(`src/instrumentation.ts`, `AUTO_MIGRATE=false`로 끌 수 있음). 배포 로그에 `[migrate] 스키마가 최신입니다`가 찍히면 된 것입니다. 수동으로 하려면 노트북에서 `DATABASE_URL='<운영 DB URL>' pnpm db:migrate`.

6. 배포가 끝나면 **Settings → Networking**에서 도메인을 만듭니다. Railway 기본 도메인도 HTTPS가 붙어 있고, 회사 도메인을 쓰려면 CNAME만 추가하면 됩니다.
7. 배치 3개는 **앱이 스스로 돕니다**(`src/lib/scheduler.ts`). 별도 크론 서비스를 붙일 필요가 없습니다. `/api/health`의 `scheduler`가 `true`면 된 것입니다(배포 로그의 `[batch] 스케줄러 시작 …`으로도 확인).

   | 배치 | 기본 주기 | 조절 변수 |
   |---|---|---|
   | 메신저 웹훅 전송 | 60초 | `SCHEDULER_OUTBOX_SEC` |
   | 알림톡 발송 | 300초 | `SCHEDULER_ALIMTALK_SEC` |
   | 보관기간 지난 회원 익명화 | 매일 04시 | `SCHEDULER_RETENTION_AT` |

   인스턴스를 여러 대로 늘려도 Postgres 자문 잠금으로 한 대만 돕니다. 끄려면 `SCHEDULER=off`.
   외부 스케줄러(Cloud Scheduler, cron-job.org)를 따로 쓰고 싶으면 `SCHEDULER=off`로 끄고 `JOB_SECRET`을 넣은 뒤 헤더 `x-job-secret: <JOB_SECRET>`로 `POST /api/jobs/{outbox,alimtalk,retention}`을 호출하면 됩니다. 두 방식을 같이 켜도 자문 잠금 덕분에 중복 발송은 나지 않습니다.
8. 백업: Railway Postgres는 일 단위 스냅샷이 있습니다. 추가로 주 1회 로컬에서 `scripts/backup.sh`를 돌려 덤프를 따로 보관하면 안전합니다.

## 2. GCP 절차

`docs/03_운영_가이드.md`의 배포 절과 `deploy/cloudbuild.yaml`을 따릅니다. 요약: Cloud SQL(PostgreSQL 16) 생성 → Secret Manager에 환경 변수 → Cloud Build로 이미지 빌드·마이그레이션 Job·Cloud Run 배포 → Cloud Scheduler로 배치 3개 → GCS 버킷(`STORAGE_DRIVER=gcs`). Cloud Run 최소 인스턴스는 1로 두어 첫 요청 지연을 없앱니다.

## 3. 사내 서버 절차

```bash
cp deploy/.env.production.example deploy/.env.production   # 값 채우기
docker compose -f deploy/docker-compose.yml --env-file deploy/.env.production up -d --build
```

Caddy가 `SITE_ADDRESS` 도메인으로 HTTPS 인증서를 자동 발급하므로 80·443 포트가 외부에서 닿아야 합니다. 배치와 백업(매일 03:30 `./backups`)은 compose 안의 scheduler·backup 서비스가 처리합니다.

## 4. 공통: 최초 데이터

1. **본사 계정과 기본 규칙**. 사용자가 없는 상태에서 `https://<도메인>/setup`을 열면 본사 계정과 첫 지점을 웹 화면에서 만들 수 있습니다. 첫 계정이 생기면 이 화면은 닫힙니다. 터미널을 선호하면 아래 부트스트랩 스크립트도 같은 일을 합니다. 시드는 가상 데이터용이므로 쓰지 않습니다.

   ```bash
   DATABASE_URL='<운영 DB URL>' pnpm exec tsx scripts/bootstrap.ts \
     --hq-login hq --hq-name "본사운영" --hq-password "<10자 이상, 영문+숫자>" \
     --branch-code DT2 --branch-name 동탄2 --seats 77 --rounds 11 \
     --manager-login dt2manager --manager-name "<지점장 이름>" --manager-password "<10자 이상>"
   ```

   본사 기본 벌점 규칙 6개와 현황판 항목 5개도 비어 있으면 함께 만듭니다.
2. **시트 적재**. 지점의 구글시트 5개를 xlsx로 받아 노트북에서 운영 DB를 향해 실행합니다. 계정과 설정은 두고 업무 데이터만 다시 넣으므로 전환일 아침에 최신 시트로 한 번 더 돌려도 됩니다.

   ```bash
   DATABASE_URL='<운영 DB URL>' pnpm exec tsx scripts/migrate-sheets.ts --branch DT2 --dir ~/Downloads \
     --members "고객정보시트_....xlsx" --counsel "(동탄) 집중관리일지 -2026.09.xlsx" \
     --board "게시용 회원생활관리 시트_....xlsx" --meals "식사 주문시트_....xlsx" --worklog "조교근무일지(2026)_....xlsx"
   ```

   근무일지에서 만들어진 직원 계정은 비밀번호가 없으니 설정 › 사용자에서 정해 줍니다. 회원만 옮길 때는 이관 화면(회원 › CSV 이관)으로도 됩니다.
3. **지점장 로그인 후 설정 점검**: 좌석 구역·결번, 회차 시간표, 벌점 규칙, 현황판 항목, 식사 단가·마감, 근무 타임, 멘토·조교 계정과 PIN.
4. **현황판 링크 발급**(설정 › 지점·현황판)을 매장 모니터 PC 브라우저에 넣고 전체화면으로 둡니다. 크롬 키오스크 모드(`chrome --kiosk <링크>`)가 편합니다.

## 5. 기기와 계정

- **조교 태블릿**: 크롬으로 접속해 "홈 화면에 추가"를 하면 앱처럼 열립니다. 조교 계정 하나로 로그인해 두고 PIN 전환으로 사람을 바꿉니다. 화면 잠금 시간을 길게 두세요.
- **지점장·멘토**: PC 브라우저. 비밀번호는 10자 이상, 영문·숫자 포함이며 5회 틀리면 10분 잠깁니다.
- **본사**: `hq` 계정으로 지점 전환과 전 지점 요약을 봅니다. 새 지점은 설정 › 지점 관리에서 만듭니다.

## 6. 알림톡 (선택, 계약 후)

1. 카카오 비즈니스 채널 개설 → 알림톡 발신 프로필 등록 → 딜러(NHN Cloud 또는 Solapi) 계약.
2. 딜러 콘솔에서 템플릿을 등록하고 승인(보통 1~3일).
3. 승인된 템플릿 코드와 본문을 설정 › 알림톡 템플릿에 등록하고, 서비스 환경 변수에 `ALIMTALK_PROVIDER`와 키를 넣은 뒤 재배포.
4. 본인 번호로 1건 테스트 발송 후 실사용.

## 8. 운영 중 확인

- 매일: `/api/health` 응답(업타임 모니터에 등록), 라운딩 회차 수, 알림톡 실패 건.
- 매주: 백업 덤프 존재, 미수 정산, 만료 임박 회원.
- 매월: 근무 월 집계 본사 확인, 식사 월 정산, 감사 로그 훑기.
- 문제 발생 시 되돌리기: Railway는 이전 배포로 Rollback 버튼, DB는 스냅샷 복원 또는 `pg_restore --clean` (`scripts/backup.sh` 주석 참고).

## 9. 아직 없는 것

에러 모니터링(Sentry 등)은 붙어 있지 않습니다. 초기에는 호스팅의 로그 화면으로 충분하지만, 지점이 늘면 붙이는 것을 권합니다. 오프라인에서 앱을 새로 여는 기능(서비스 워커)도 없으므로 매장 와이파이가 끊기면 이미 열린 라운딩 시트의 입력만 보존됩니다.
