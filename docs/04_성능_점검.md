# 성능 점검 (2026-09-05)

## 목적

설계서 10장의 비기능 목표(지점 10개 · 지점당 80석 · 체크 레코드 연 200만 건 · 목록·현황판 p95 1초 이내)를 실제 데이터 규모로 확인한다.

## 환경

| 항목 | 값 |
|---|---|
| 데이터 | 지점 10, 회원 900(등록 800·상담 100), 좌석 800, 라운딩 세션 10,110, **체크 1,054,400건**(12주치, 일별 4항목 + 회차 12), 상담일지 8,160건 |
| DB | PostgreSQL 17 (로컬 brew, Apple Silicon). `checks` 테이블 299MB(인덱스 포함) |
| 앱 | Next.js 16 운영 빌드(`next start`), 서버와 DB가 같은 기기 |
| 도구 | `pnpm perf:seed`(시드, 67초), `pnpm perf:measure`(서버 측 함수 시간), curl(HTTP 왕복) |

Cloud SQL로 가면 쿼리당 네트워크 왕복 1~5ms가 더해진다. 아래 수치에 쿼리 수 × 2~3ms를 더해 보면 운영 예상치에 가깝다.

## 실행 계획 확인

- 현황판·대시보드의 `checks` 조회는 `checks_branch_date_idx`(지점 + 일자) 비트맵 인덱스 스캔으로 한 주 6,880행만 읽는다(전체 105만 행 중). 실행 시간 3~4ms.
- 회원별 조회는 유일 인덱스 `checks_uq`(회원, 일자, 항목, 회차)의 선두 컬럼으로 회원 한 명의 1,318행만 읽는다. 0.6ms.
- 순차 스캔은 어느 조회에서도 나타나지 않았다. 추가 인덱스는 필요 없다.

## 용량 전망

| 기준 | 체크 건수 | `checks` 크기(추정) |
|---|---|---|
| 현재 측정 | 105만 (12주) | 299MB |
| 1년 (지점 10) | 약 450만 | 약 1.3GB |
| 3년 (지점 20) | 약 2,700만 | 약 8GB |

Cloud SQL 기본 디스크(10GB부터 자동 증가)로 3년은 문제없다. 2천만 건을 넘기면 `checks`를 월 단위 파티션으로 나누거나 2년 지난 데이터를 요약 테이블로 옮기는 것을 검토한다. 현황판·대시보드는 항상 최근 1주만 읽으므로 총량이 늘어도 응답 시간은 유지된다.

## 권고

1. **현황판 응답 크기(339KB/분)**: 매장 모니터 1대당 하루 약 490MB. 회선이 넉넉하면 그대로 두고, 필요하면 `points: 0`인 셀을 생략하고 키를 축약해 1/3로 줄일 수 있다. 우선순위 낮음.
2. **본사 전 지점 요약**: 지점당 5개 쿼리를 순차 반복한다. 지점 20개·Cloud SQL 기준 약 300ms로 예상되며 여전히 목표 안이다. 지점이 30개를 넘으면 지점별 집계를 한 번의 GROUP BY 쿼리로 합친다.
3. **라운딩 일별 조회(37ms)**: 12회차 × 80명 = 960셀을 서버에서 조립한다. 문제는 없으나 회차 수를 늘리는 지점이 생기면 가장 먼저 커지는 화면이다.
4. **Cloud Run 콜드스타트**: 첫 요청이 40~90ms 더 걸리는 것은 로컬에서도 보인다. 운영에서는 min 인스턴스 1로 콜드스타트를 막는다(운영 가이드 2항).
